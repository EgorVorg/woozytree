# Спайк: чтение MFT NTFS (2026-11-21)

**Задача:** Task 4, Plan 1. Сравнить два способа чтения таблицы MFT и выбрать один.
**Том для замеров:** `C:` (NTFS, сектор 512 Б, кластер 4096 Б, запись MFT 1024 Б).
**Код спайка:** `src-tauri/src/bin/dump_mft.rs`, режим `--spike` (throwaway, в рабочий путь не входит).

## Геометрия тома C:

| Параметр | Значение |
|---|---|
| Байт в секторе | 512 |
| Байт в кластере | 4096 |
| Размер записи MFT | 1024 |
| Стартовый LCN `$MFT` | 786 432 |
| Серийный номер тома | `0xe8960b86960b548a` |
| `$MFT` реальный размер | 924 319 744 Б (881 МиБ) |
| Число записей в `$MFT` | 902 656 |
| Фрагментация `$MFT` | 6 экстентов (не непрерывен!) |

## Замеры полного чтения всех 902 656 записей

| Способ | Время | Скорость | Ошибок |
|---|---|---|---|
| (а) сырое последовательное чтение по runlist `$DATA` | **0.775–0.787 с** (4 замера) | ~1135 МиБ/с | — |
| (б) перебор `FSCTL_GET_NTFS_FILE_RECORD` | **1.96 с** (3 замера, 2.2 мкс/запись) | — | 0 из 902 656 |

Первый замер (б) дал аномально большое время — 8.708 с (9.6 мкс/запись), а замер на
20 000 записях перед ним — 7.8 мкс/запись. Повторные замеры на том же коде стабильно
дают 1.96 с (2.2 мкс/запись), поэтому 8.7 с считаем выбросом (холодный кэш/антивирус
на первом запуске утилиты). Для сравнения берём повторяемые значения: 0.78 с против 1.96 с.

Оба способа укладываются в «единицы секунд» на этом томе, но способ (а) стабильно быстрее
в ~2.5 раза (а на первом, «холодном» замере — в 11 раз).

## Решение: способ (а) — прямое последовательное чтение `$MFT`

Почему, хотя оба способа укладываются в ограничение:

1. **Стабильно быстрее.** 0.78 с против 1.96 с (×2.5). Время (а) линейно по объёму MFT
   (≈1135 МиБ/с), у (б) добавляется ~2.2 мкс на каждую запись: на диске 1 ТБ с 2 млн файлов
   это ~1.8 с против ~4.4 с только на ioctl, ещё до разбора записей.
2. **Нужная форма данных.** Задаче 5 нужен поток сырых записей фиксированного размера;
   (а) отдаёт срезы буфера без копирования, (б) — буфер на каждую запись плюс системный
   вызов на каждую запись.
3. **Разбор `$MFT` всё равно нужен.** Число записей (для прогресса и оценки) берётся из
   реального размера `$DATA`, т.е. загрузочный сектор и запись №0 парсятся в любом случае.
   Способ (б) этой работы не отменяет, а только добавляет к ней свой цикл ioctl.
4. **Меньше системных вызовов:** сотни `ReadFile` по 1 МиБ против `DeviceIoControl`
   на каждую запись.

## Как устроено чтение (способ а)

1. Открыть `\\.\C:` на чтение (нужен администратор).
2. Прочитать загрузочный сектор → байты в секторе/кластере, размер записи MFT (смещение 0x40:
   знаковое; `<0` — `1 << -n`, `>0` — кластеров на запись), стартовый LCN `$MFT` (0x30).
3. Прочитать запись №0 (по LCN из заголовка), снять fixup (USA), найти неименованный
   нерезидентный атрибут `$DATA` (0x80) → runlist (mapping pairs) и реальный размер.
4. Последовательно прочитать экстенты runlist'а кусками по 1 МиБ, нарезать на записи
   по `record_size`, остановиться на реальном размере `$MFT`.

## Грабли (важно для задачи 5)

1. **Сырое чтение тома требует выравнивания.** Смещение и длина запроса должны быть кратны
   размеру сектора. Поэтому загрузочный сектор читается сразу 4096 байтами (иначе на 4Kn-дисках
   чтение 512 байт упадёт с `ERROR_INVALID_PARAMETER`), а запись №0 — целым кластером.
2. **Fixup (Update Sequence Array) обязателен.** Последние 2 байта каждого сектора записи на диске
   заменены номером последовательности; без замены на сохранённые байты разбор атрибутов может
   прочитать мусор. Для последовательного чтения всех записей fixup не нужен — важно только
   для разбора записи №0 (и понадобится в задаче 5 для разбора остальных записей).
3. **`$MFT` фрагментирован.** На `C:` это 6 экстентов, разбросанных по всему тому; читать
   «от стартового LCN до конца» нельзя — только по runlist из `$DATA`.
4. **Число записей берётся из реального размера `$DATA`,** а не из выделенного: выделенный
   размер округлён до кластера и содержит хвост вне записей.
5. **`$ATTRIBUTE_LIST` не разбирается.** Если `$DATA` самого `$MFT` окажется разбит на
   extension-записи (атрибут 0x20), текущий разбор увидит только базовую запись. На `C:` такого
   нет (6 экстентов в одной базовой записи). Для задачи 5 это ограничение зафиксировано.
6. **`FSCTL_GET_NTFS_FILE_RECORD`** возвращает валидные записи для всех номеров 0..N-1,
   ошибок на `C:` не было; буфер вывода — `NTFS_FILE_RECORD_OUTPUT_BUFFER`, данные начинаются
   со смещения 12 (не 16: `UCHAR[1]` идёт сразу за `ULONG`).
